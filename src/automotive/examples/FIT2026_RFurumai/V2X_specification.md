# V2X Evaluation Specification

## 1. Scope

This document defines the simulation assumptions for NR-V2X sidelink V2V and
Uu/MEC-based V2N2V cooperative perception evaluation.  It is intended to prevent
future mismatches between implementation, plots, and presentation claims.

The target scenario is a Japanese highway-like environment with vehicle-dense
sections.  The final evaluation should avoid artificial background load when
possible and should generate congestion through dense vehicle clusters and real
V2X messages.  The evaluation compares:

- V2V only: NR-V2X PC5 sidelink broadcast.
- V2N2V only: Uu uplink, MEC forwarding, and Uu downlink.
- Hybrid V2X: V2V as the primary low-latency path and V2N2V as a complementary
  recovery/extension path.

## 2. Message Models

### 2.1 CPM

CPM is generated by `CPBasicService` from perceived objects in the LDM.  The
current implementation includes perceived objects when at least one of the
following ETSI-style conditions is met:

- The object is newly detected.
- The object moved more than 4.0 m since the last CPM inclusion.
- The object speed changed by more than 0.5 m/s.
- The object heading changed by more than 4 deg.
- The maximum CPM inclusion interval has elapsed.

Therefore, CPM size is object-count dependent and time varying on the V2V path.
This behavior must be preserved for V2V evaluations.

For V2N2V, fixed-size accounting is not sufficient for the final model.  The
V2N2V model must either use the actual CPM size or estimate payload size from
the number of forwarded objects.

The current lightweight MEC model uses the latest observed CPM serialization
size from `CPBasicService` for V2N2V byte accounting.  If no CPM has been
generated yet, it falls back to the configured average packet-size value.

### 2.2 CAM

CAM is treated as periodic awareness traffic.  It contributes to baseline
channel load in dense traffic.  If CAM is enabled in an evaluation, its interval,
packet size, and route must be logged explicitly.

### 2.3 DENM

DENM is event-driven burst traffic.  If DENM is enabled, the event-generation
model, burst duration, repetition interval, and priority must be stated.  DENM
is not part of the current FIT evaluation unless explicitly enabled.

## 3. V2V Path Model

V2V uses NR-V2X PC5 sidelink broadcast.

Required properties:

- One transmission may be received by multiple nearby vehicles.
- Channel load is measured through CBR.
- Packet loss may arise from sidelink congestion, interference, distance, and
  channel conditions.
- CPM payload size varies with perceived object count.

Required logs:

- V2V TX/RX packets.
- V2V bytes.
- CBR average/max.
- Packet loss by importance class.
- CPM object count and CPM size.
- RMR candidate/deleted object count.
- AoI violation count/rate.

## 4. V2N2V Path Model

V2N2V consists of:

1. Vehicle to gNB/MEC uplink.
2. MEC processing.
3. MEC to target vehicles downlink.

### 4.0 Source-Controlled Communication Parameters

Communication parameters must be traceable to a paper, standard, measurement
dataset, or clearly marked provisional assumption.  Scenario parameters such as
vehicle count and initial positions may be designed for evaluation purposes, but
communication latency, capacity, and packet-loss parameters should not be tuned
without recording the source.

The capacity values above are not claimed as measured highway throughput.  They
are source-derived service-rate proxies for the lightweight queue model:

`capacity = bandwidth * spectral_efficiency`

where the current main default uses `20 MHz * 4.5234 bit/s/Hz = 90.468 Mbps`.
This is a service-rate proxy for the lightweight queue model.  V2N2V uses Uu,
so its actual bandwidth is determined by the mobile network operator and
deployment; it is not legally fixed by the ITS PC5 band.  If a specific Uu
carrier bandwidth is assumed, it must be stated explicitly and recorded here.

The final model must not treat V2N2V as a lossless fixed-delay link.  It must
include at least:

- Generation-time-based AoI.
- E2E delay distribution with tail latency.
- Downlink fanout caused by unicast forwarding to multiple receivers.
- Uplink and downlink load accounting.
- Capacity-limited queueing delay.
- First-transmission radio loss and retransmission recovery for UL/DL.
- Drop reasons.

### 4.1 Unicast Fanout

Unlike V2V broadcast, V2N2V downlink forwarding is modeled as receiver-wise
unicast.  If one sender's CPM is forwarded to `N` target vehicles, the downlink
load is counted as `N` transmissions.  This is a key disadvantage of V2N2V under
dense traffic.

Required fanout logs:

- Receiver count per uplink CPM.
- Total forwarded receiver count.
- Mean/p90/p95/p99 fanout.
- Downlink bytes after fanout.

### 4.2 Delay Model

The baseline V2N2V E2E delay should be decomposed as:

`D_e2e = D_ul + D_mec + D_dl + D_queue`

The current lightweight implementation uses an empirical percentile delay model
by default.  It samples from piecewise-uniform ranges fitted to the adopted
measurement targets:

- mean around 39.40 ms.
- p90 around 59.86 ms.
- p99 around 120.33 ms.

The older clipped normal delay model remains available through
`mec-ideal-delay-model=normal`, but it should not be used for final evaluation
because it underrepresents heavy-tail delay.

### 4.3 Capacity and Queue Model

The model must account for uplink and downlink capacity separately.  Downlink is
expected to be the critical bottleneck because MEC fanout creates many
receiver-wise transmissions.

Required parameters:

- `mec-ideal-capacity-model`
- `mec-ideal-bandwidth-mhz`
- `mec-ideal-spectral-efficiency-bpshz`
- `mec-ideal-max-queue-delay-ms`

The main evaluation uses the source-derived capacity proxy listed in Section
4.0.  The default profile is 90.468 Mbps for both UL and DL, and the
180.936 Mbps profile is reserved for bandwidth-sensitivity evaluation.  Other
infrastructure traffic such as DENM and MAPEM should be modeled explicitly or
handled by a separate sensitivity run, not by undocumented capacity tuning.

### 4.4 UL/DL Radio Loss and Retransmission Model

The lightweight model must not claim to reproduce full 3GPP PHY/MAC behavior.
It does not calculate SINR, MCS adaptation, HARQ process timing, RLC buffers, or
scheduler-specific BLER.  Instead, it uses a literature-based abstraction:

1. A Uu uplink or downlink packet first encounters a first-transmission loss
   probability.
2. If the first transmission fails, a bounded number of HARQ/RLC-style
   retransmission attempts is applied.
3. Each retransmission attempt adds delay.
4. If no retransmission succeeds, the packet is counted as final radio loss.

Required parameters:

- `mec-ideal-ul-first-loss-rate`
- `mec-ideal-dl-first-loss-rate`
- `mec-ideal-retx-success-prob`
- `mec-ideal-max-retx`
- `mec-ideal-retx-delay-ms`

The main profile uses initial BLER `0.10`, max retransmissions `4`, and
retransmission delay `3 ms`.  The per-retransmission success probability is
derived as `0.53` so that the final residual loss is approximately `0.5%`:

`P_final = 0.10 * (1 - 0.53)^4 = 0.0049`.

For a URLLC-like low-loss sensitivity run, use initial BLER `0.01`; the same
retransmission model then produces a much smaller final residual loss.

Required logs:

- Uplink first-transmission losses.
- Downlink first-transmission losses.
- Uplink retransmission recoveries.
- Downlink retransmission recoveries.
- Uplink final radio losses.
- Downlink final radio losses.
- Retransmission delay mean and p90.

This decomposition prevents double-counting packet loss: first-transmission BLER
does not directly mean final loss if retransmission recovery succeeds.  The
published explanation should describe this as a "literature-fitted abstract Uu
loss and retransmission model", not as a full 3GPP link-level simulation.

Required logs:

- MEC uplink packets/bytes.
- MEC forwarded downlink packets/bytes.
- Capacity-induced delay mean/p90/p99.
- Capacity queue drops.

Future extension logs:

- UL/DL load ratio.
- UL/DL queue length.
- UL/DL queue delay split.

## 5. AoI Definition

AoI must be based on the message generation time, not the receive time.

`AoI = t_now - t_generation`

For received packets:

`E2E delay = t_receive - t_generation`

For recognition freshness:

`t_now - t_generation <= AoI_threshold`

Recommended thresholds:

- 50 ms.
- 100 ms.
- 200 ms.
- 500 ms.

All thresholds should be evaluated from the same simulation run.  A packet that
misses a stricter threshold can still be counted as satisfying a looser
threshold.

Required AoI logs:

- AoI samples.
- AoI mean.
- AoI p50/p90/p99.
- AoI achievement rate for 50/100/200/500 ms.
- High-priority AoI achievement rate for 50/100/200/500 ms.
- Low-priority AoI achievement rate for 50/100/200/500 ms.
- AoI violation rate for each threshold.  This is the complement of the AoI
  achievement rate among received MEC updates, not a radio packet-loss rate.
- Capacity queue drops as the first implemented deadline-related drop signal.

## 6. Drop Reasons

Packet loss, stale updates, and recognition-state failures must be decomposed by
cause.  They must not be reported as one undifferentiated packet-loss rate.

Required drop categories:

- Uplink radio loss: a Uu uplink transmission that still fails after the
  configured retransmission attempts.
- Downlink radio loss: a Uu downlink transmission that still fails after the
  configured retransmission attempts.
- Queue overflow.
- Capacity deadline miss.
- AoI violation: a received update whose generation-time-based AoI is larger
  than the selected threshold.  The packet was received, but it is stale.
- TTL violation: an object-recognition state that was not refreshed within the
  recognition TTL.  This is an application-level recognition failure, not a
  radio packet loss.
- No receiver in forwarding range.
- Policy-filtered object.
- Never received: an object that was expected for recognition but has never
  been received by the evaluating vehicle.  This is a diagnostic category for
  explaining ORR degradation; it should not be treated as a primary packet-loss
  metric because it may include range, routing, policy, and radio effects.

Recommended reporting groups:

- Radio reliability: V2V sidelink radio loss, V2V high/low-priority sidelink
  radio loss, MEC UL final radio loss, MEC DL final radio loss, and combined
  MEC radio final loss.
- Update success/failure: V2V update failure and MEC update failure.  These are
  application-level expected-update outcomes and must be kept separate from
  final radio loss counters.
- Freshness: AoI violation rates for 200/300/400/500 ms.
- Recognition continuity: TTL violation rate.
- Diagnostics: never-received rate and no-receiver forwarding count.

### 6.1 MEC Forwarding Range Sensitivity

`MEC_FORWARD_RANGE` is the service/application range used by the MEC to select
which nearby vehicles receive forwarded cooperative-perception updates.  It is
not modeled as the Uu radio propagation distance between UE and gNB.

Therefore, the 200 m / 500 m sensitivity analysis should be explained as a
MEC delivery-scope and downlink-fanout sensitivity analysis.  Increasing the
range mainly increases the number of downlink receivers, downlink bytes,
downlink busy ratio, queueing delay, AoI violations, and TTL violations.  In the
current lightweight V2N2V model, distance-dependent Uu SINR/BLER is not
explicitly modeled, so any degradation observed at 500 m should not be claimed
as direct distance-propagation loss.

For the current evaluation, it is acceptable to prioritize bandwidth/fanout
congestion over distance-dependent V2N2V packet loss, because the modeled
MEC range changes the number of forwarded receivers much more directly than it
changes Uu radio distance.  If distance-dependent Uu loss is needed, a separate
UE-gNB distance/SINR or distance-bin loss model must be added.

## 7. Comparison Methods

The final presentation should include at least:

- V2V only.
- V2N2V only.
- Hybrid V2V/V2N2V.
- Hybrid with adaptive low-priority V2N2V forwarding.

The purpose is to show that V2N2V alone provides wide-area recovery but suffers
from fanout, tail delay, and AoI violations, while V2V alone suffers from local
congestion and packet loss.  The hybrid method should be evaluated as a
complementary design, not as V2N2V replacement.

## 7.1 Main Scenario Policy

The main final-presentation scenario should use:

- 100% communication vehicles.
- Dense vehicle clusters.
- Opposing clusters crossing at a controlled time and location.
- No artificial NR background traffic, if CPM/CAM can create sufficient CBR.
- No moving high-load zone in the main evaluation.

If CPM alone does not create sufficient congestion, CAM may be enabled as
periodic baseline traffic.  DENM should be reserved for a separate burst-load
evaluation.

## 8. Implementation Policy

`v2v-hybrid-nr-v2n2v.cc` remains the main implementation until a cleaner
NR-only successor is created.  Legacy 802.11p/DSRC code should not be removed
blindly because route switching, metrics, and logging still reference `dsrc`
names internally.

A future refactor should:

- Create a new NR-only file after the specification is stable.
- Rename legacy `dsrc` metrics to neutral names where they actually mean
  primary/legacy route.
- Remove 802.11p only after equivalent NR-only metrics and tests exist.
- Preserve existing result reproducibility by keeping the old file unchanged or
  archived.
