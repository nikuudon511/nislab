## 2. Current Research Claim

- Claim: Hybrid V2V/V2N2V needs RMR to make the V2N2V path useful under dense highway traffic.
- Why it matters: V2V alone suffers from sidelink loss/congestion, while V2N2V alone suffers from MEC downlink load, tail delay, and AoI violations.
- Current confidence: medium. The old best result supports the claim, but key runs used low-priority TTL 0.5 s and should be rerun with unified TTL 0.2 s.

## 3. Summary of `0727進捗.md`

- Main comparison: V2V only, V2N2V only, Hybrid baseline, and Hybrid+RMR.
- V2V only reached about 61.3% ORR, but packet/radio loss remained high.
- V2N2V only reached about 13.9% ORR and suffered severe MEC AoI/update failure.
- Hybrid baseline improved over V2V only to about 69.7% ORR, but MEC AoI and update failure were still large.
- Hybrid+fixed RMR 10/20/40 reached about 98.6% ORR in the old result set.
- The main explanation was not average CBR reduction. The key factor was reducing CPM payload and MEC downlink load, which improved MEC AoI and valid update success.
- V2V only + RMR did not improve ORR; it reduced packet/radio loss but also reduced useful recognition opportunities.
- Hard Guarded RMR failed because protecting too many high-priority MEC fanout pairs overloaded MEC downlink and worsened AoI.
- The next research direction was to use soft guard, prediction-aware RMR, strict TTL sensitivity, and seed sensitivity.

## 7. Result Interpretation

- What improved: Hybrid+RMR can dramatically reduce MEC AoI and update failure compared with Hybrid baseline.
- What got worse: Stronger or differently applied RMR can reduce low-priority ORR by removing useful recognition opportunities.
- Main bottleneck: MEC downlink required load and tail delay, not mean V2V CBR.
- Evidence against alternative explanations: V2V only + RMR did not improve ORR, so the improvement is not simply from applying RMR to sidelink.
- Remaining uncertainty: The headline best result used low-priority TTL 0.5 s and should be rerun with high/low TTL 0.2/0.2.

## 7.1 Hybrid Route-Control Interpretation

Current implementation facts:

- `v2n2v-adaptive-probability` maps to `hybrid-v2v-v2n2v` with MEC object
  policy `adaptive-probability`.
- In low-CBR state, the hybrid controller keeps NR sidelink/V2V as the primary
  route.
- In warning or congested CBR state, MEC V2N2V is activated as a complementary
  route.
- With `hybrid-high-dual-tx=true`, high-priority information can be transmitted
  over both V2V and V2N2V.
- NR/V2V uses `RMR_FORWARDING_PRIMARY`; MEC duplicate mode uses
  `RMR_FORWARDING_DUPLICATE`. In duplicate mode, the MEC CPM path is not the
  same as fanout suppression; it can carry the CPM object payload on the
  complementary path.
- Low-priority V2N2V forwarding is controlled by `adaptive-probability`, with
  the forwarding probability decreasing as predicted/measured CBR approaches
  `hybrid-cbr-max`.

Interpretation rule:

- Do not describe Hybrid+RMR as an RMR-only effect.
- Do not describe Hybrid as simple bandwidth addition.
- Describe it as role separation: V2V broadcast is the efficient primary path,
  V2N2V is a MEC-assisted complementary path, high-priority objects may get
  route diversity through dual transmission, and RMR/policy control keeps the
  complementary path fresh enough to be useful.
- Route policy must be treated as a sensitivity axis, especially
  `hybrid-high-dual-tx`, `mec-adaptive-low-max-prob`, `mec-recovery-policy`, and
  the CBR thresholds.


Default assumptions:

- `SIM_TIME=30`
- MEC capacity proxy scales as `SCALE^2`
- NR channel-rate proxy scales as `SCALE`
- MEC background packet size scales as `SCALE`
- NR background packet size stays at 500 bytes because per-vehicle source count
  already scales with vehicle count
- RMR delete budget scales as `SCALE`, giving default `3/5/10`

Reasoning:

- V2V channel load is closer to sender-count scaling.
- V2N2V downlink load is closer to `senders * receivers`, so it is closer to
  quadratic in vehicle scale when road length and forwarding range stay fixed.
- RMR delete budget is per CPM and should scale with expected local object
  count, not with total downlink fanout.

This profile is useful only if it approximately preserves the main ordering:

```text

V2V only: middle ORR
Hybrid+RMR: high ORR
```

Interpretation caution:

- Do not interpret `Hybrid+RMR - V2V+RMR` as a simple V2N2V contribution, because ORR is a union-style recognition metric with overlap between paths.
- Use V2N2V only+RMR to test whether the V2N2V path can become independently useful after RMR.
- Use Hybrid+RMR to test whether V2V and V2N2V complement each other under the same clean settings.
- Separate route-control effects from RMR effects in later sensitivity analysis,
  because current Hybrid+RMR includes high-priority dual transmission and
  low-priority adaptive V2N2V forwarding.

## 9.5 MEC Object-Payload RMR Interpretation Note

Status: implementation interpretation note.

In the current lightweight MEC object-payload RMR model, `RMR_DELETE_HIGH=40`
means that the MEC CPM packet-size accounting removes up to 40 object entries
from the payload-size estimate.  It is not yet a full object-ID-level deletion
model on the MEC path.

Observed V2N2V-only + object-payload RMR example:

| Time | Active vehicles | MEC candidates | Candidates per vehicle | Deleted last | Deleted per vehicle | Delete fraction |
|---:|---:|---:|---:|---:|---:|---:|
| `t=18 s` | 200 | 10974 | 54.9 | 7697 | 38.5 | 70.1% |
| `t=20 s` | 200 | 10304 | 51.5 | 7663 | 38.3 | 74.4% |

Interpretation:

- The `40` delete budget is strong in this scenario: each vehicle has roughly
  50-55 MEC candidate objects, and about 38 objects per vehicle are removed
  from the payload-size estimate under high-load conditions.
- `mec_rmr_payload_deleted_total > 0` and
  `mec_rmr_fanout_deleted_total = 0` confirm that this is payload accounting,
  not receiver fanout suppression.
- The current MEC object-payload model does not record every deleted object ID,
  but new runs include high/low-priority aggregate accounting columns:
  `mec_rmr_payload_deleted_high_*` and `mec_rmr_payload_deleted_low_*`.
- For paper wording, say "MEC object-payload RMR reduces the CPM payload-size
  accounting" unless/until ID-level deletion is implemented.

Implementation-cost note:

- Recording every deleted object ID to CSV can become expensive because MEC
  forwarding is receiver-wise fanout and the candidate count is large.
- Maintaining aggregate counters is much cheaper and likely sufficient:
  `mec_rmr_payload_deleted_high_total`,
  `mec_rmr_payload_deleted_low_total`, and optional per-window rates.
- If ID-level debugging is needed, use a sampled or optional debug log rather
  than always writing every deleted ID.

## 9.6 Lightweight Synergy Validation Plan

Status: design memo before lightweight simulation.

Recent full-scale evidence already covers two failure baselines:

- V2N2V-only + object-payload RMR remains poor under high vehicle density:
  ORR stays around 14%, MEC update failure reaches 100%, and AoI is effectively
  broken even though the link is idealized.
- V2V-only + RMR improves neither enough nor in the same way as Hybrid+RMR:
  ORR is around 44%, CBR remains high, and the V2V required-load diagnostic is
  above the 6 Mbps normalization denominator.

The next useful question is therefore not simply whether either single path
fails, but whether Hybrid+RMR creates a route-control synergy beyond adding more
capacity to one path.

Hypothesis:

- V2V is efficient for local broadcast and immediate high-priority sharing, but
  suffers from high CBR and sidelink packet/update loss at high density.
- V2N2V is useful for wider-area selected delivery, but receiver-wise MEC
  downlink fanout makes all-object delivery inefficient under dense traffic.
- Hybrid+RMR can outperform single-path capacity relaxation because it assigns
  different roles to the two paths: high-priority information can be duplicated
  across V2V and V2N2V, while lower-priority or redundant object payload is
  suppressed on the congested path.

Lightweight simulation should first test trends, not final paper numbers:

- Compare V2V-only + RMR against V2V-only + RMR with a relaxed V2V load
  denominator.  This checks whether the Hybrid gain can be explained by simply
  increasing V2V capacity.
- Compare V2N2V-only + RMR against V2N2V-only + RMR with relaxed MEC bandwidth.
  This checks whether the Hybrid gain can be explained by simply increasing
  V2N2V capacity.
- Compare both against the normal Hybrid+RMR profile.  The desired evidence is
  that route-aware use of two paths improves ORR/AoI/loss more efficiently than
  either single-path relaxation.

Additional idea for later implementation:

- For V2N2V, DLBR-aware object-count capping may be more natural than V2V-style
  RMR deletion.  Because MEC delivery is receiver-wise fanout, limiting each
  downlink CPM to 5 or 10 high-value objects should reduce DL load almost
  linearly with payload size times receiver count.
- This should be treated as a future V2N2V-specific control knob, not as an
  immediate replacement for current object-payload RMR results.
- For V2V, the opposite direction may be more effective under very high CBR:
  instead of making every vehicle transmit a smaller CPM, select fewer
  representative transmitters and let each selected CPM carry enough useful
  objects.  This reduces packet count, contention opportunities, and PHY/MAC
  overhead, whereas payload-only RMR mainly shortens each packet.
- Literature already treats CPM object selection, redundancy suppression,
  message-generation control, and fixed-size/risk-based object selection as
  known scalability tools.  Therefore, the future-work angle should not claim
  that "fewer transmitters" or "object selection" is new by itself.  The more
  useful claim is path-specific resource use: V2V should prioritize reducing
  sender count or generation frequency when the shared broadcast channel is
  saturated, while V2N2V should prioritize reducing per-receiver CPM payload
  because MEC downlink fanout multiplies payload size by receiver count.
- Candidate discussion wording: RMR has different leverage depending on the
  communication path.  On V2V broadcast, payload reduction alone may not lower
  CBR enough when packet count and contention dominate.  On V2N2V, payload
  reduction directly suppresses MEC downlink load because each forwarded byte is
  replicated across receivers.  A future extension should therefore combine
  representative V2V transmitters with MEC-side object-count capping.

## 9.7 Related-Work Story for V2N2V Complement Path

Status: writing memo.

Collective Perception Service shares object information detected by vehicle
sensors through CPMs so that vehicles can perceive objects outside their own
sensor field of view.  In dense traffic, however, many vehicles periodically
transmit CPMs and duplicate information about the same objects, causing channel
congestion and packet loss.

Related approaches:

- Delooz et al. compare ETSI-style Redundancy Mitigation Rules and evaluate how
  deleting redundant object information from CPMs reduces communication load.
- Yamasaki builds on Frequency-, Dynamics-, and Distance-based RMR and considers
  driving environment and object type when selecting deletion targets, improving
  pedestrian recognition while exposing recognition/load tradeoffs.
- Huang et al. model redundancy in highway collective perception and adjust
  per-object transmission probability based on position, vehicle density, and
  road geometry to suppress redundant transmission.
- Sepulcre et al. improve scalability by combining CPM generation rules,
  redundancy control, and object organization to avoid frequent transmission of
  small CPMs.
- Figueiredo et al. select CPM objects under congestion based on deviation from
  predicted trajectories, prioritizing objects with higher information value.

These works mainly improve what is sent over the V2V CPM path: message content,
generation rules, object selection, or redundancy suppression.  They reduce
payload or unnecessary transmissions, but do not remove the shared-medium nature
of high-density V2V broadcast.  When CBR is high, contention, hidden terminals,
and simultaneous transmissions can still prevent necessary updates from arriving
within the recognition TTL.

This study therefore introduces a gNB-MEC-assisted V2N2V path as a complement to
ordinary V2V CPM sharing.  V2V remains suitable for immediate local broadcast,
while V2N2V can use MEC aggregation to deliver information beyond the local
sidelink neighborhood and compensate for information lost on the congested V2V
path.  V2N2V is not treated as a simple replacement: the MEC downlink fanout can
itself become a bottleneck, so the intended contribution is a hybrid path-control
approach that exploits the different strengths and bottlenecks of V2V and
V2N2V.
